03 · Do nth engineers (invited users) need a separate experience?

No. They need a different first contact, not a separate onboarding, for three reasons:

  • They did not choose anything. A bot showed up in their pull request. Onboarding they did not ask for is noise; the PR itself has to carry the explanation.
  • They may have no LaunchDarkly seat, and they cannot change the account-wide switches either way. There is nothing in settings for them to do, so nothing should route them there.
  • Their whole experience is four surfaces: the check, the comment, one OAuth click, and the review page. If those say what it suggests, what approving does and under whose account, that doing nothing creates nothing, that the check does not block merge, and who approves when the author has no seat, the job is done (scope S3).

The one in-app addition is a one-time notice on their first visit after a repo they commit to is connected. It is true that rejecting has no consequence: Reject declines the proposal and nothing is created, pushed, or scheduled.

04 · Constraints on Nov 16

  • No plan check in code. Access is six dogfood flags targeted at five design-partner accounts; GA for self-serve is a targeting change. The beta promo banner targets Enterprise and Guardian plan types only.
  • Prerequisites the product cannot remove.
    • GitHub only. Org-level install, so a GitHub org admin. Private repos only.
    • One LD account per install; one project per repo.
    • Every PR author authorizes GitHub once.
    • A release policy per project, or "Policy needed" and the rollout retries for three weeks then expires.
    • A metric for any automatic pause; there are no auto-metrics.
    • Environments start when deployed code evaluates the flag; the webhook trigger is API-only.
    • GenAI terms accepted or BYOK for the agent.
  • What approve does. One commit under the approving member's GitHub connection; the flag under their LD permission; the release scheduled; LD approval workflows bypassed at GA. Approval required is on by default and not changeable in the UI. Bot authorship with the member as co-author is an ask, not built.
  • GitHub is not required for the core. The flag's Release tab can create and start a release, pause, and resume. For a trialist today the Create dialog has no Create button (the default release configuration is a Release Engineering dogfood flag whose only live variation is "CATFOOD ONLY"), and without GenAI opt-in no footer at all. Nothing seeds a release policy. Trial projects have Test and Production.
  • The real screens.
    • Home is the product roadmap only (sim hero removed Oct 13): heading, four picker tiles, a numbered lane, a learning pane. All hardcoded data in a Foundation-owned package.
    • Welcome survey: the first-action question is a five-option toggle group whose value preselects the Home lane. "Guarded release" is already a UI-only value.
    • Flags list: five seeded example flags for trials, and a banner slot above the list where "SDK not connected" renders today.
    • The "announcement banner" package is the customer admin's own tool. Our channels are the one-time popover (catalog empty, flag off, Shown and CTA Clicked events) and the promo banner variants in the top banner stack.
    • Automation settings exists at /settings/release-autopilot behind enable-factory-settings. Three ways in, all behind the flag: settings rail (Configuration group), legacy settings nav, a link in the GitHub App drawer. "Map projects to repositories" is that page's installed state, not a separate page.
    • The flag's Release tab, its Create release dialog, and the "Flag releases" dashboard exist behind flags; the dashboard still reads a mock API.
  • Billing has no percentage construct.
    • The catalog prices flat cents per block; the only percentage anywhere is the 50% Kubernetes discount.
    • Plans picker: "Choose a plan," the "Add CodeControl" bundle selector, three cards.
    • Customize: a read-only rate table (Product, Included, Standard rate).
    • Check out: no line items. A collapsed plan summary, "Monthly price: Usage-based," "Due today."
  • Known failure modes. No result when the classifier recommends nothing, so "people think it didn't run." The bot comment is "a tough blurb of text to parse." Every PR author must set up. Suggestion acceptance is 17 to 19%. Internal teams dislike the PR noise and guarded defaults without traffic. Tim expects no customer in production before January; auto-release has the most confidence, the classifier the least.
  • Not at GA. Slack notifications, approvals integration, plan authoring UI, auto-metrics, setup wizard, a recommend-only mode. The releases dashboard reads a mock API.
  • Foundation's box. Audit log yes (account-level entries 30 days, environment-level unlimited); approvals and custom roles no.

A pull request opens

Release Autopilot reviews every pull request on a connected repository and reports a result, including "no flag needed." It does not block merge.

It proposes a flag and a release plan

The comment says what it suggests, what happens if you approve, whose account the commit lands under, and that nothing happens if you don't.

A member approves

Approving the flag pushes one revertible commit to the branch. Approving the release schedules it for after merge. Approval is required on every pull request. Release Autopilot does not use your LaunchDarkly approval workflows at launch.

The release runs itself

After merge, each environment starts when your deployed code evaluates the flag and follows the project's release policy. Connect a metric and it pauses on regression. Pause by hand any time.

It cleans up after itself

Once the flag has no targeting changes for 14 days and serves one variation everywhere, a cleanup pull request removes it from code; you merge it, then archive the flag from the Release tab. Every step is in the audit log under the approving member.

07 · What the crits changed

Three personas (a fintech senior engineer as the nth engineer, a VP Engineering at a two-year Foundation customer, and a LaunchDarkly designer paired with the Autopilot eng lead verifying against gonfalon) reviewed three drafts. The changes that survived:

  • The three-rung trust ladder is gone; approvalRequired exists only on Auto-flag and is on by default. Two switches plus a statement.
  • Every safety claim is written to the code: pause only with a metric, environments start on flag evaluation, approvals bypassed at launch, commits under the approving member, revertible. Manual pause holds; guarded auto-rollback needs a metric.
  • Author of record is the IC's deciding factor; bot authorship is a v0 ask with a stated fallback, and the sentence is identical on the settings page, the comment, the review page, the email, and the walkthrough.
  • Owners do not log in, so the hand-off and the launch-day email are primary. "Included until Feb 1" needs a stated default. Hidden beats fake for the dashboard.
  • Invented numbers and promises removed. Trial environments are Test and Production. Foundation has the audit log (30-day account-level window). Writers with GitHub auth can map repos.
  • Billing is drawn in the only shape the catalog carries: the bundle selector as the opt-in pattern and the inclusions block as the "free until" slot.
  • Every v0 is an edit to a real screen with the change outlined, and every scope shows Current first, with its problems listed under each frame.
  • Draft 7: survey before Home with a hover tooltip; an alternate left-to-right hero; role-specific banner and flags-list card for existing customers; the nth-engineer notice mocked in section 04; "Map projects to repositories" clarified as the installed state of the existing settings page.
